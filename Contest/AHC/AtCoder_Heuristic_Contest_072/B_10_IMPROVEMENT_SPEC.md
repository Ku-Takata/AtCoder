3. 全盤面BFSを置き換える「小領域の状態一致探索」。独立な操作を間から除いて探索する拡張も含む。
4. 別実験として、候補解の内容による重複判定と、後処理時間の配分を改善する。

今回作成したのは設計書のみ。解答コードの新規実装・変更、コンパイル、解答プログラムの実行は行っていない。既存コード、問題文、引き継ぎ資料、保存済み出力を調査した。

## 4. 改善A：差分区間検証を共通部品にする

### 4.1 狙い

現行の幾何学的短縮は、変更が操作列の後半にしかなくても、毎回配列全体をコピーして最初から実行する。既にprefix盤面を作っている関数でも同様である。

これを次の形式に統一する。

```text
元の列 = prefix + old_interval + suffix
候補列 = prefix + replacement  + suffix
```

元の区間は半開区間 `[a, b)` とする。離れた2手を編集する場合も、その間の保持する操作を含めて1区間として表現できる。

例：手iを変更し手jを削除するなら、`a=i, b=j+1`、replacementは「変更後の手i、その後の元のi+1～j-1」。

### 4.2 キャッシュとAPI

```rust
// 設計用の型。既存Op・BitBoard・Gridを使う。
struct TraceCache {
    boards: Vec<BitBoard>,       // boards[t] = 元のt手を実行した盤面
    cleared: Vec<usize>,         // 元のt手までの累積帰巣数
    endpoints: Vec<(u16, u16)>,  // 各操作の出発・着地点
}

enum CheckResult {
    Accept,
    Reject,
    BudgetExpired,
}

// replacementは小さな固定バッファまたは再利用Vec/iteratorで渡す。
fn validate_patch(
    ops: &[Op], trace: &TraceCache,
    a: usize, b: usize, replacement: &[Op],
    grid: &Grid, target_cleared: usize,
    deadline: Instant,
) -> CheckResult;
```

まずは次の簡単な実装でよい。

1. `board = trace.boards[a]`、`cleared = trace.cleared[a]`。
2. replacementを正確に実行。不正ならReject。
3. 元の `ops[b..]` だけ実行。
4. 合法性と `cleared >= target_cleared` を確認。
5. Acceptになって初めて `ops.splice(a..b, replacement)` を行う。

候補列全体の `clone()`、`remove()` の繰り返し、変更前prefixの再実行をなくす。replacementには長くても既存の探索窓程度の操作しか入らない。

### 4.3 追加高速化：元の盤面に合流したら検証を終了

replacement実行後の盤面が `trace.boards[b]` と等しいなら、残りは既に検証済みのsuffixなので受理できる。違っていても、suffixの途中で元と同じ盤面になれば、その時点で終了できる。

全400マスを毎手比較する必要はない。

1. `[a,b)` 内の元の操作とreplacementの出発・着地点の和集合を列挙する。
2. replacement実行後、その和集合についてだけ `trace.boards[b]` と比較する。
3. 違うマスを400bitの差分集合に入れ、個数を保持する。
4. suffixの元の手tを両方の時間軸で進めるとき、変わり得るのはその出発・着地点の2マスだけ。それらについて新盤面と `trace.boards[t+1]` の一致・不一致を更新する。
5. 差分集合が空なら合流した。帰巣数も `cleared + (trace.cleared[last] - trace.cleared[t+1])` で元の目標を満たすことを確認してAccept。

根拠：壁と巣は固定であり、移動中に飛び越す塔の内容を操作は参照しない。動的に読み書きするのは両端の塔だけ。帰巣も両端だけで起こる。

### 4.4 必須の注意

- 色0の8匹と空塔を区別するため、比較には必ず高さを含める。
- colorsの未使用上位bitは0に正規化する。`occupied_mask` は高さから一貫して更新する。
- ハッシュ一致だけで合流判定しない。高さと有効色列の完全一致を使う。
- 時間切れはRejectとは別に扱い、現在の候補評価を捨てて検証済みの解を返す。
- 受理後、TraceCacheは変更地点以降を再構築する。古いsuffix盤面を次の候補で使わない。
- `prune_ops` の逆順走査でprefixの一部を再利用できても、合流判定用suffixには最新のキャッシュが必要。
- B01は途中解を `target_cleared` で扱う箇所がある。共通検証器を「常に全匹帰巣前提」に変えてはいけない。
- 最初の実装では候補列挙順・SA・窓幅を変えず、高速検証器だけを切り替えられるようにする。

## 5. 改善B：空き中継点を含み、合法なkを全列挙する2手置換

### 5.1 現行にない具体的な近傍

現在の `orthogonal_2hop_jumps` は出発・最終地点が同じ行または列だとスキップする。一方、同一直線上を扱う `coriding_leap_jumps` は、中継点に元から塔があることを要求する。

そのため、**同一直線上にある空きマスを経由する2手の移動**を、これらの関数は列挙しない。

また、既存の2～3段マクロは原則として `k = 距離 - 1` の候補だけを作る。土台を余分に残すことで後続が成立する候補は取りこぼし得る。

### 5.2 手計算できる例

以下は大きな盤面の局所部分で、6マスはすべて床。他の塔は関与しないとする。

```text
P(a)   X(.)   Q(A)
R(.)   S(.)   T(.)
```

Pにはaが1匹、Qはaの巣。元の操作列は `P→R→S→T→Q` の4手、すべて `k=0, l=1`。

`P→X→Q` の2手に置き換えられる。Xが空でも問題なく、前後の盤面は完全一致する。

現行の直接ジャンプではPの高さ1から距離2を飛べない。直交2手は同一行なので対象外、相乗り2手はXが空なので対象外。現行LNSではXがactive_cellsに入らず、Xに着地できてもXから次の手を生成できない。この例は、既存の関数群を増速するだけでは埋まらない探索の穴を示している。

これは保存100件から得た削減例ではなく、提案の正しさを説明する局所例である。

### 5.3 実装する関数

`complete_2hop_jumps` を既存後処理と同じインターフェースで追加する。

初版では元の連続区間を対象とし、区間長3～8手、出発P=`ops[a]`の出発点、最終Q=`ops[b-1]`の着地点とする。最大40手などへの拡張は最初から行わない。

候補中継点X：

- P,Qが異なる行・列：2つの直交コーナー。
- P,Qが同じ行・列：P,Q間にあるすべての床マス。空きマスも含める。
- X=PまたはX=Qは除外。
- 各区間が壁を通らないことを `max_reach` で確認。
- 同一直線上のP,Qの外側への寄り道は初版では省略してよい。

ここで全列挙するのは、上記の幾何学的候補に対する合法なkの組である。全盤面上のあらゆる2手列を列挙するという意味ではない。

中継点ごとの候補生成：

```text
original = trace.boards[a]
for k1 in [l1-1, height(original,P)-1]:
    after1 = original
    P→Xをk1でapply_opする
    不正ならcontinue
    // ここでは着地と出発の帰巣が既に済んでいる
    for k2 in [l2-1, height(after1,X)-1]:
        after2 = after1
        X→Qをk2でapply_opする
        不正ならcontinue
        validate_patch([a,b), [op1,op2])
        成功したら短い列を採用し、キャッシュを更新
```

開始値が終了値を超える範囲は空とする。各kは最大8候補なので、1中継点あたり最大64組。

最初に `(k1,k2)=(l1-1,l2-1)` を試してよいが、それだけで打ち切らない。`after1` の実際の高さを使い、帰巣前の高さを2手目の高さとして使わない。

区間全体を置換するので、途中の独立操作を誤って捨てた候補は検証で落ちる。より効率よく拾う拡張は次節で扱う。

### 5.4 計算量の制御

- 完全一致する2手置換を先に受理し、合流しない候補は改善Aのsuffix検証に回す。
- `ops.clone()` はせず2手の固定配列を使う。
- 区間長は3～8、1回の持ち時間は初期値30ms。
- 時間を使い切ったら最後に受理済みの列を返す。
- 既存関数はまず残す。候補生成を完全に包含したと確認できるまで削除しない。

## 6. 改善C：小領域の状態一致探索

### 6.1 現行LNSとの違い

現行の `reopt_window` は各ノードに約2KBの全盤面を持ち、active_cellsから生成した手の着地点はその集合外でもよい。しかし集合外へ移った塔は、そこが次の出発候補に入らない。

新しい探索では、初めから**両端に使うマス集合Rを定義し、その中の全マスを出発候補にも使う**。状態はR内だけを持つ。途中にある壁の検証には元のGridを使う。

目標は「評価値がよい盤面」ではなく、**元の区間を終えた盤面と全く同じ状態**。元より短い手数で到達した場合だけ置換する。

### 6.2 まず連続窓版を完成させる

初版の設定：

| 項目 | 初期値・方針 |
|---|---|
| 元の窓長 | 3、4、5、6手 |
| 置換後の探索深さ | 最大 `min(4, 元の手数-1)` |
| Rの上限 | 12マス |
| 補助マス | 最大2マス |
| 1窓の展開数 | 合計2,000ノードまで |
| 1窓の上限時間 | 約1msを初期値とする |
| 全体の持ち時間 | 初期値50ms |

これらは未調整の初期設定。効果確認前に窓・ノード数・時間を一斉に増やさない。

Rには元の区間の全出発・着地点を必ず入れる。追加する補助マスは次の順で最大2マス。

1. マス対を結ぶ短い2手経路の空き中継点・空きコーナー。
2. 開始時に塔があり、長距離ジャンプの踏み台になり得る近傍マス。

補助マスも開始・終了の状態を固定する。借りた踏み台を動かしたまま終える候補は不可。集合が大きすぎる場合は、必要マスを削らず、その窓自体をスキップする。

### 6.3 局所状態と遷移

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash)]
struct LocalState {
    cells: [u64; 12],
}

// 各要素：下位32bitに色列、32bit目以降に高さ。
// R外と未使用要素は必ず0。1状態96バイト。
```

Rのローカル番号と盤面番号を相互変換する配列を持つ。Rのマス対について同一行・列、方向、距離、壁なしを前計算する。

遷移はR内の全出発点・全k・合法な着地点を列挙する。

1. `0 <= k < h`。
2. `1 <= l <= k+1`、かつ壁なし。
3. **帰巣する前の** `g+(h-k) <= 8`。
4. 上側の色列を反転して着地点へ追加。
5. 出発点・着地点の両方を帰巣処理。

途中で通る床マスはR外でもよい。そこに塔があっても合法性は変わらない。ただし着地点は必ずR内にする。

### 6.4 探索方法

最初は深さ制限付きDFSの反復深化でよい。深さ0での一致も確認する。

- 深さ上限1、2、3、4の順に探索し、見つけたら終了。
- 各反復のvisitedは `LocalState -> 到達済みの最小深さ`。状態本体の比較を行うHashMapを使う。
- ノード予算は深さを増やすたびに復活させず、窓単位の合計で管理する。
- 残りr手で終了状態と違うマスがD個なら、`D > 2*r` を枝刈りする。1手が変える塔は高々2つなので安全。
- いずれかの色の現在個数が終了状態の必要個数より少なくなったら枝刈り。帰巣は不可逆なので復元不能。
- 同一状態への即時往復を省く。
- 終了状態と一致するマスを増やす候補を先に試してよいが、悪化する候補をその理由だけで除外しない。
- 帰巣を含むので、逆操作を単純に宙返りさせる双方向BFSにはしない。

`D/2` の下界は弱いが、正しさが明確。最初から不確かな距離評価を枝刈り条件に使わない。

成功したら、元の `[a,b)` と置換後でR内が完全一致する。R外には双方とも変更がないため全盤面も一致し、suffixはそのまま利用できる。

### 6.5 拡張：間にある独立操作を除いて探索する

連続窓だけでは、関係する3～6手の間に無関係な操作が挟まると探索が大きくなる。各操作が読む・書くのが両端だけであることを利用し、独立操作を残したまま、関連操作だけを置換する。

定義：元の時間区間 `[a,b)` とマス集合Rについて、次を満たすようにする。

- 選択する操作：少なくとも片方の端点がRにある操作。
- 選択した操作の**両端点**をRに含める。
- 残す操作：両端点がR外にある操作。

この条件を作るには、区間内の操作を走査し、Rと交差する操作の相手側端点をRに追加する。Rが増えなくなるまで走査を繰り返す。後からRに入ったマスに以前の操作が触れている場合があるので、**1回の前向き走査だけで完了としてはいけない**。

実装の初期上限：元の時間区間は最大24手、選択操作は3～6手、Rは12マス。上限を超えたらその候補を捨てる。

候補区間は、各マスの端点としての出現時刻リストから生成する。手aの両端に次に触る手を追い、関連操作が3、4、6個になる時点をb候補とする。各aにつき最大3候補程度とし、全ての時刻対を列挙しない。閉包を作った結果、選択手数が想定を超えた場合は上限判定し直す。

補助マスの追加でも独立性が変わる。初版では、`[a,b)` 内でどの操作の端点にもなっていないマスだけを補助マスとして追加する。端点になる補助マスを使いたいなら閉包計算からやり直す。

成功後の出力は次の順に組み立てる。

```text
元の prefix [0,a)
短縮した関連操作列
[a,b) の非選択操作を元の相対順序のまま
元の suffix [b,T)
```

正当性：非選択操作はRを読み書きしない。新操作はR内の塔だけを読み書きする。互いに順番を交換してよく、区間終了時のR内・R外がそれぞれ元と一致する。飛行経路が互いのマスを通っていても、途中の塔は障害物にならないため問題ない。

最初の実装では受理時に区間全体を実際に再生し、`trace.boards[b]` と全盤面一致することも確認する。これは閉包・インデックスの実装ミスを検出する重要な確認である。

## 7. 改善D：候補の多様性と時間配分は別の実験にする

現在は同じ長さの候補が全て重複扱いになる。また、先頭候補のrun_pipelineに共有deadlineの全てを渡すため、後続候補が評価されないことがある。

改善案：

1. 長さと操作列ハッシュで候補を識別し、ハッシュ一致時には実際の列も比較する。同じ長さでも異なる内容なら保持候補とする。
2. SAの全体最良解は必ず1枠確保する。現状の「同じ長さの別解が既にあるためsa_best_opsを追加しない」挙動をなくす。
3. 新しい最良手数が出るたびに、候補を現在の最良+8手以内に整理する。完全帰巣していない候補を長さだけで選ばない。
4. 最大6候補のうち、まず3枠を生の手数で選ぶ。残りは先頭の色順や各色の処理戦略が異なる候補を優先し、同手数解も許す。
5. SAの受理判定や近傍分布は変えない。候補保存のためにSA用乱数を余計に消費しない。

候補を増やすだけでは悪化し得るので、別の時間配分案と組にする。

- 生の手数上位3候補だけを短く前処理する。各候補の予算は残り後処理時間の約1/8。
- 前処理はprune、cycle、straight/rayを中心とし、重いLNSを実施しない。
- 前処理後の最良1候補に残り時間を集め、2手置換・小領域探索まで進める。
- 全ての処理済み候補と生の全体最良解を保持し、最後は検証済みの最短列を選ぶ。

同長異内容を区別しても、最終スコアが必ず改善するわけではない。保存済みB_08/B_09のケース別差は、探索・時間制限の揺れも含む。この変更は改善A～Cと分離して評価する。

## 8. 実装順序と時間設計

変更を識別できるように、以下を独立したソースまたは切替フラグとして用意する。`B_09.rs` と保存済み出力は上書きしない。

| 名前 | 変更内容 |
|---|---|
| B_10_fast | 改善Aのみ。候補列挙・SA・後処理の呼び順はB_09と同じ |
| B_10_bridge | fast + 改善B |
| B_10_local | bridge + 改善C。連続窓版と独立操作を除く版を切替可能にする |
| B_10_pool | local + 改善D。別実験として扱う |

最も小さく始めるなら `B_10_fast` と `B_10_bridge` の2本を先に実装する。新しい解法の主要部分は `B_10_local`。SAの全面的な作り直しや色順探索の変更は今回の主題ではない。

A44でlocalまで入れる場合の、最初の時間配分例：

| 開始からの時刻 | 処理 |
|---|---|
| ～1,400ms | 既存の初期スクリーニング＋SA |
| ～1,650ms | 高速化した既存prune/cycle/幾何学的短縮。旧LNSはここでは呼ばない |
| ～1,680ms | 改善Bの2手置換 |
| ～1,730ms | 改善Cの小領域探索 |
| ～1,750ms | 最後のprune/cycle、短い検証済み解の確定 |

これは実測前の配分例。各段階が早く終われば次へ進む。新しい段階自身には30ms/50msの持ち時間上限も設け、早く開始したからといって固定終了時刻まで全部使わせない。消費しなかった時間は後段または別候補に回せる。

bridgeだけの場合は、小領域探索用50msを従来後処理へ戻す。fastだけの場合は元の時間配分を維持する。

時間に関する必須事項：

- 関数には実際の締切 `Instant` を渡し、関数内で時計をリセットしない。
- 大きい内側ループでも32～64候補ごとに時間を確認する。局所探索は展開数と時刻の両方で止める。
- SAループ末尾の評価などは1,400msを超えて完了することがある。残り時間が少なければ新しい探索を飛ばす。
- 常に現在の「合法性・目標帰巣数を確認済みの解」を保持する。タイムアウト時に途中の置換を反映しない。
- `best_final_ops.unwrap()` 依存をなくし、生の検証済み最良解を初期fallbackにする。
- B01へ新探索を統合するのは別段階。B01には外側solveと内側chokudai_searchで別々の開始時刻がある。統合時には共通の締切へ直す必要があるが、フォールバックの帰巣処理を単に途中で切ってはいけない。

**同じ操作列に対する採用済み置換は手数を増やさないが、同じ制限時間内でB_09を必ず上回る保証とは異なる。** 計算時間の再配分や探索順の変化で、別のよい候補を失うことはあり得る。

## 9. 今回優先しない案

### 同色を巣の手前でまとめて射出するだけの案

単色の塔を距離2から運ぶなら、塔全体を1マスずつ2回動かすと2手。下に1匹を残して上だけ2マス飛ばすと、その土台の回収が必要になる。単純な例では射出1手＋土台の歩行2手で3手になり、むしろ悪化する。

既に `try_bulk_direct_nest_launch` と `try_bulk_hop_and_launch` もある。一括射出を追加するだけでは新規性も改善根拠も弱い。土台の回収まで含む厳密な置換で評価する。

### 4-hop専用の幾何学的パターン追加

既存の直交2手関数は、時間的に離れた終点も見て長い区間を2手に置換している。「4手のジグザグ」という名前だけでは新しい近傍にならない。空き中継点、全kの列挙、独立操作の温存を先に補う。

### 窓幅・ノード数の一律増加

既存の失敗記録では、候補検証が重くなって時間内に調べられる解が減っている。今回は窓を広げる前に、区間再生・局所状態・依存関係で計算を減らす。

### 異色の強制相乗りや事前クラスタリングの全面変更

回収コストや塔の順序の悪化が既に報告されている。まず既存の生成解を正確な後処理で改善する。

## 12. 何が確実で、何を実測するのか

設計から確認できること：

- 変更前prefixの再実行と候補ごとの全配列コピーは不要。
- 空き中継点を通る同一直線上の2手経路は、現行の幾何学的候補に欠落がある。
- 両端の塔以外には動的依存がないため、独立操作を除いた局所探索は正当化できる。

実測が必要なこと：

- 100件における実際の削減手数。
- 高速化で増やせる探索回数と、局所探索の成功率。
- 30ms・50msという予算や候補プールの配分が適切か。
- 2秒以内で32,194を安定して下回り、さらに32,000未満へ届くか。
