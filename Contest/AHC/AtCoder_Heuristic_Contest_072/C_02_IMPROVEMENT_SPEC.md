## 1. 結論

次の改善では、**C_01が出す最良解をいったん確定し、残った時間でその解をさらに短縮する**。この追加段階を本書ではtail探索と呼ぶ。

優先順位は以下とする。

1. **必須：最良解へのtail探索。** C_01のSA・候補評価を維持し、終了時の未使用時間を活用する。既存短縮の再適用と逆順の局所探索を行う。
2. **推奨：tail用局所探索の高速化。** 残り1手の直接判定、遷移直後の枝刈り、候補バッファの再利用、同じ窓の再探索の抑制。
3. **拡張：帰巣のない区間に限定した前後方向の探索。** 前から2手、後ろから最大3手を探索し、現行の置換後最大4手では届かない5手の置換を探す。

最初からSA時間・候補プール・B01固有探索を同時に変えない。前回の改善Dで提案した「生の手数上位3候補に絞る」案も、今回は優先しない。

今回行ったのは既存ファイルと保存ログの分析、要件定義のみ。解答プログラムの実行・改変・コンパイル、新しい解の生成は行っていない。以下の新方式の改善量は未測定。

## 5. 必須要件T：C_01の最良解確定後にtail探索を追加する

### T-1. 既存探索を保護する

次の構成にする。

```text
C_01と同じ初期スクリーニング・SA
    ↓
C_01と同じ候補生成・候補評価・最良解選択
    ↓
checkpoint_opsを確定（既に合法・全帰巣を検証済み）
    ↓
残り時間だけでtail探索
    ↓
checkpoint以降の検証済み最短列を出力
```

`checkpoint_ops` と `checkpoint_score` を保存する。tail中は**操作数が真に減り、合法性・全帰巣が維持される変更だけを反映する**。

受理条件：

```text
new_length < current_length
かつ
（元のsuffixを維持できる完全状態一致
  または差分区間検証で全帰巣まで確認済み）
```

時間切れ・未発見・予算不足なら、最後の検証済み列を返す。

保証できるのは `final_score <= checkpoint_score`。別実行のC_01と完全に同じ結果になる保証ではない。ソースサイズや実行速度の差で時間制限型SAの反復数が変わる可能性は残る。

### T-2. 締切

- C_01の開始から1,750msという既存の終了目安を引き上げない。
- tail探索の締切は1,745msを初期値とし、最後の確認・出力に余裕を残す。
- mainとa44の開始時刻に差がある。既存SAの時計を変更せず、tailでは必要ならmainから渡した締切との小さい方を使う。
- 残り5ms未満ならtailをスキップする。
- 内側の候補生成にも、全体で通算32～64候補ごとの時刻確認を入れる。
- 予算を使い切ること自体を目的にしない。未探索の仕事がなくなれば終了してよい。

### T-3. 最初の実装は既存関数の再適用だけでよい

`--tail=legacy` として以下を実装する。

1. 現在の最良列に、straight/ray/orthogonal/coriding/crankの短縮とbridge・prune/cycleを再適用する。
2. 最初のこの段階には `min(15ms, tail開始時の残り時間/5)` を目安に配分する。各関数に共有する部分締切を渡す。
3. 残り時間でcompactを再適用する。最初は**操作列の後ろから**窓を選ぶ。
4. 改善した場合、短いbridge/prune/cycle処理を挟む。
5. その後は順方向と逆方向を交互にする。何も変わっていない同じ窓を同じ条件で何度も探索しない。

既存幾何学的関数を長く回しただけでtail予算を全て使わないようにする。局所探索へ使う時間を残す。

逆順走査は「解答の操作を逆実行する」という意味ではない。**元の順方向の窓最適化を、後半の窓から試す**という意味である。

### T-4. 走査状態とキャッシュ

tailの1セッション内で現在の列・TraceCache・走査方向・カーソルを保持する。短い時間で打ち切った処理を再開するとき、毎回a=0へ戻さない。

置換により操作の添字が変わるので、次を守る。

- traceを変更地点以降再構築する。
- 古い操作番号だけを持つ窓候補キューは破棄するか、列のversion不一致で無効化する。
- 再開カーソルを現在の操作数へ収める。
- 初版では、区間の前後数手を再訪し、次の走査で全体を拾い直す簡単な方式でよい。
- trace更新が時間切れなら、それ以上の候補探索は行わない。採用済みの操作列自体は保持する。

## 6. 推奨要件K：tail用compact探索を軽くする

初版ではC_01の通常候補評価で使うLocalSearchをそのまま残し、別の `CompactSearchFast` をtailだけに用いる。通常候補評価への適用は、効果を分離して確認してから別設定で行う。

### K-1. 残り1手を直接判定する

現在状態Sと目標Gで異なるマス集合をDとする。

- Dが空なら長さ0で成功。
- Dが3マス以上なら1手では到達不能。
- 1手の出発点pは、必ずDに含まれ、`height(S,p) > height(G,p)` を満たす。出発塔は必ず低くなるため。
- Dが2マスなら、着地点qはもう一方のマスに限られる。
- Dが1マスなら、着地点qの状態は操作前後で同じでなければならない。qはR内の巣に限定できる。飛んだ塊が帰巣して塔が元に戻る場合がある。

上記のp,qについて、静的な射線が存在するか調べ、全合法kを列挙して正確な両端帰巣を行う。Sからこの操作を実行してGに完全一致するなら成功。

重要：巣上の出発点では、土台が帰巣して `height(G,p) < k` になることがある。**kを目標高さへ固定してはいけない。** `distance-1 .. height(S,p)-1` を全て試す。

API例：

```rust
enum SearchOutcome {
    Found(Vec<Op>),
    Exhausted { max_depth: u8 },
    NodeLimit { completed_depth: Option<u8> },
    TimeLimit { completed_depth: Option<u8> },
}

fn solve_one_move(
    current: &LocalState,
    goal: &LocalState,
    geometry: &LocalGeometry,
    budget: &mut SearchBudget,
) -> SearchOutcome;
```

実際には0手・1手だけを返す軽い専用型でもよい。残り1手の全子状態をVecへ貯めてソートする処理をなくす。

残り2手では1手目を通常生成し、残り1手をこの判定へ渡す。帰巣を伴う窓にも適用できる。

### K-2. 子状態の枝刈りを、候補配列へ入れる前に行う

現在コードでは子状態を候補配列に積んでソートした後、再帰呼び出し内で多くを捨てている。

遷移で変わるマスはp,qだけなので、不一致マス数を次のように更新できる。

```text
next_diff = current_diff
            - old_mismatch(p) - old_mismatch(q)
            + new_mismatch(p) + new_mismatch(q)
```

残りr手で `next_diff > 2*(r-1)` なら、その子は候補配列へ入れない。状態一致なら直接成功として扱ってよい。

色個数の下界確認も、毎回R全体を数え直す必要はない。現在の色別個数を保持し、両端の帰巣で減った分だけ更新する。目標で必要な個数を下回った色があれば捨てる。帰巣のない遷移では色個数は変わらない。

これらは正しい下界による枝刈り。「目標に近づかなかった」という理由だけで候補を消さない。

### K-3. ノードごとのメモリ確保と大きい候補コピーをなくす

現行の `moves: Vec<(diff, LocalState, Op)>` は候補ごとに96byteのLocalStateを含み、毎ノード生成・ソートされる。

代わりに、候補には次を持つ。

```rust
struct LocalCandidate {
    src: u8,
    dst: u8,
    k: u8,
    ray_id: u8, // または方向・距離
    next_src: u64,
    next_dst: u64,
    next_diff: u8,
}
```

- 深さごとに候補バッファを再利用する。再帰中の子が親のバッファを上書きしないこと。
- 再帰する候補だけ、親状態へ2マスの差分を適用する。状態をコピーするならその時だけ96byteをコピーする。
- あるいは2マスを更新して探索後にundoする。その場合は色個数・ハッシュ・不一致数も確実に戻す。
- ソートは小さい候補構造体またはインデックスに対して行う。まず安定した通常ソートでよい。
- Rの静的射線表は探索の各ノードで作り直さない。
- 時計と統計の更新を最内周で過剰に行わない。締切確認は十分細かく、統計はローカル変数へ集計して後で加算する。

C_01の物理関数を比較用として残し、性能のために高さ・反転・両端帰巣の検証を省略しない。

### K-4. 深さ制限は必要なところから始める

反復深化の最初の深さを、少なくとも `ceil(開始時の不一致マス数/2)` にできる。開始状態=目標状態の0手判定は別に行う。

最初は置換後最大4手を維持する。高速化と深さ増加を混ぜて結果を不明瞭にしない。

ノード予算は「生成した遷移」「DFS呼び出し」「枝刈り後の展開」を分けて計数する。C_01のcompact_nodesと新しい展開数を同じものとして速度比較しない。時間と成功窓数を主に比較する。

## 7. 推奨要件M：窓の結果を再利用する

tailで同じ列に何周も処理をかける場合、前と全く同じ局所問題を再探索しない仕組みが必要。

### M-1. キー

窓キャッシュのキーは以下。

```text
Rのマス数
昇順に正規化したRの盤面座標
その順で並べた開始LocalState
その順で並べた目標LocalState
探索で許した領域・遷移ルールの識別情報
```

盤面・巣・壁は1入力内で固定なので、キャッシュ自体を入力単位にすればキーへ全盤面を入れる必要はない。Rの順序を変える場合は状態・操作のローカル番号も必ず変換する。

ハッシュは索引用であり、キー本体を比較する。R外の塔を着地点に使う探索を将来追加した場合は、このキーでは不十分になる。

### M-2. 保存する結果

- 成功：見つかった合法な短い経路。
- 完全探索済み：そのR内で深さd以下に解がなかったという証明済み上限。
- 予算切れ：完全探索できた深さまで。中断した深さについて「解なし」とは記録しない。

**2,000ノードや1msで止まったことは到達不能の証明ではない。** 現行のOption返却をそのまま失敗キャッシュに使わない。

候補の追加補助マスが変わればRが変わるため別問題。探索深さを増やす場合も、浅い深さの失敗だけで打ち切ってはいけない。

同じ予算切れ窓を同じ走査内で何度も試さないための一時的な印を別に持ってよい。その印は「解なし」とは区別し、深さ・予算・Rを変えて試す際には無効にする。

### M-3. 適用と上限

- 初版はtail内だけ共有する。通常候補評価への共有は別設定。
- 最大4,096窓程度を初期上限にする。満杯なら新規保存を止める簡単な方式でもよい。
- cached経路が現在の選択操作数以上なら短縮には使わない。
- 毎回その区間の独立性・閉包条件を確認する。キャッシュ一致だけで区間の非選択操作を無視してはいけない。
- 採用時は保持した独立操作も含めて区間を再生し、現在の目標全盤面との一致を確認する。
- キー一致率は現ログからは分からない。必ずhit率・節約した探索数・キャッシュ処理時間を記録する。

## 8. 拡張要件R：帰巣なし区間の前後方向探索

K/Mの実装後、独立したスイッチとして追加する。時間だけを増やして同じ4手探索を繰り返す代わりに、新しい近傍へ進むための拡張である。

### R-1. 適用条件

- 区間の開始・終了について、R内の色別スライム数が全て等しい。
- 元の区間と同様に、選択操作がR内に閉じている。
- Rは初期上限10マス、元の選択操作は6～8手とする。
- R内の塔を途中で帰巣させる遷移は許さない。

帰巣は不可逆である。開始と終了の色個数が同じなら、正しい置換の途中で帰巣は一度も起こらない。この条件に限れば逆向きの前状態生成を扱いやすい。

巣がR内に存在していても構わない。実際の帰巣数が0であることが条件。

### R-2. 逆向き遷移の正確な作り方

Yを操作後の状態とする。元の操作がp→qだったと仮定する。

1. `k = height(Y,p)`。
2. qの上からm匹を取り出す。`1 <= m <= min(height(Y,q), 8-k)`。
3. 前状態Xを、`X[p] = Y[p] + reverse(top_m(Y[q]))`、`X[q] = bottom_(height(Y,q)-m)(Y[q])` とする。
4. 元の方向・距離lについて、壁なし、`l <= k+1` を確認する。
5. Xが安定状態であることを確認する。巣上の塔の一番上がその巣の色なら、そのXは生成対象から外す。
6. **Xから元の正方向操作 `(p,k,d,l)` を実際に適用し、帰巣数0かつ結果がYと完全一致することを確認する。**

成功したXだけをYの逆向き隣接状態とする。

飛距離の条件を逆向きの塔の高さで勝手に置き換えない。「宙返りを反対へ行えば逆操作」という実装は禁止。

### R-3. 中間状態で接続する

```text
開始状態から正方向に深さ2まで
終了状態から上記の逆方向に深さ3まで
    ↓
同じLocalStateを見つける
    ↓
合計5手以下で開始から終了へ到達
```

- 状態本体の完全一致で接続する。
- 正方向側には通常の親と操作を保存する。
- 逆方向側では、前状態Xから親状態Yへ進む「正方向の操作」を保存する。
- 経路は開始→接続状態の列に、逆方向側の親を辿って得られる正方向操作列を付ける。
- 6手以上の元の区間に対し、5手以下を発見した場合だけ採用する。
- 初期値は両探索合計4,000格納状態・1窓2ms程度。tail全体の締切が最優先。
- 各側で最小深さを保持する。予算で打ち切った場合、探索空間を網羅したとは扱わない。

これにより置換後最大4手の制限を、条件のよい窓だけで5手へ拡張する。帰巣を伴う区間にはKの順方向探索を使い、無理に逆生成しない。

### R-4. 有望度を測る

現ログには「帰巣なし6～8手窓の件数」がない。適用割合や改善手数を推測値で断言しない。対象窓数・成功数・節約手数・時間を記録し、効果がなければ無効のままにできる構成とする。
